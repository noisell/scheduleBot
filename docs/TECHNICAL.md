# Технические заметки

## Исходники и точки входа

Я сохранил историческую версию своего первого проекта. Основная точка входа — `main.py`: она подключает роутеры и middleware, удаляет webhook с `drop_pending_updates=True` и запускает polling. `main_love.py` относится к отдельному боту знакомств.

Парсер базового расписания находится в `config/schedule_pars/campus_1.py`. Парсер документов изменений и формирование ответов — в `schedule.py`. В `utils.py` расположены загрузка документов, мониторинг и уведомления. Функция `start_array` из `handlers/admin.py` объединяет два цикла проверки документов и задачи напоминаний; они не запускаются автоматически из `main.py`.

## Подготовка к запуску

Перед запуском я бы подготовил отдельное тестовое окружение:

1. Выпустил новые токены Telegram и YooMoney вместо ранее опубликованных и заполнил локальную конфигурацию по `.env.example`.
2. Создал чистую SQLite-базу командой `python scripts/init_db.py`. Для отдельного экспериментального бота предусмотрен флаг `--love`. Схемы в `schema/` содержат только структуру таблиц. Скрипт отказывается перезаписывать существующий файл.
3. Зафиксировал совместимые версии зависимостей. В исходниках используются aiogram 3, pdfplumber, requests, python-dateutil и yoomoney; файла зависимостей и закреплённой версии Python нет.
4. Импортировал базовое расписание и настроил ссылки на PDF обоих корпусов.
5. Проверил polling на отдельном тестовом боте и только затем включил мониторинг и уведомления.

Перед публикацией я удалил пользовательские SQLite-базы, Python-кэши и настройки IDE из файлов проекта и его истории. Токены, ID администраторов и платёжный адрес вынес в переменные окружения. Для сохранения структуры базы извлёк только SQL-схему, без пользовательских записей. Ранее опубликованные секреты нужно заменить у соответствующих провайдеров: очистка Git не отзывает их.

## Что я улучшил бы сейчас

Я бы выделил парсинг, нормализацию, хранение и Telegram-представление в отдельные модули, заменил позиционные списки понятными структурами данных и добавил эталонные результаты для всех PDF-примеров. Для мониторинга использовал бы неблокирующие HTTP-запросы, таймауты и атомарную замену записей.

Проверка обновлений опирается на `modified` Яндекс Диска. При отсутствии обновления цикл делает паузу 60 секунд, после успешной обработки — 600 секунд, после ошибки — 3 600 секунд. Это не мгновенное получение событий и не построчный diff документов.

Отдельно я бы проверил вычисление верхней/нижней недели: в текущей функции дата `%d.%m` получает год 1900, а опорная дата создаётся с текущим годом. Это не было частью выполненного PDF-smoke-теста и требует исправления перед новым запуском.

Боевой бот, платёжные сценарии, напоминания и рассылки в ходе подготовки документации я не запускал. Логику PDF-парсеров не менял.

## Локальная конфигурация

Создайте отдельное виртуальное окружение и установите совместимые версии зависимостей. Затем скопируйте `.env.example` в `.env`, заполните значения и загрузите их в окружение процесса. Само приложение `.env` автоматически не читает. Для Bash:

```bash
set -a
source .env
set +a
python scripts/init_db.py
python main.py
```

Используйте синтаксис Bash для значений в `.env` и отдельного тестового бота. Не запускайте polling с токеном действующего бота без намерения переключить его обработку. Чистая схема ещё не содержит базового расписания, ссылок документов и настроек: их нужно инициализировать отдельно перед полноценной работой. Версии зависимостей и сквозной запуск в этой задаче не проверялись.
